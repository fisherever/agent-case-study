# 00 · 电梯演讲

> 为什么读这篇：30 秒判断 demands_agent 值不值得继续往下看。
> 读完带走：一句话定义 + 三个最锋利的判断 + 一个最贵的教训。

## 一句话

**demands_agent 是一个把"数据需求从口述到上线"做成可验证交付流水线的内部 Agent——它真正解决的问题不是"让 LLM 写 SQL"，而是"怎么让一个会写 SQL 的 AI 不在交付这件事上撒谎"。**

## 三个最锋利的判断

这三个判断是我在这个项目里反复被打脸之后才信的，现在它们是我做任何 Agent 项目的默认假设。

**判断一：价值住在"验证"里，不住在"生成"里。**
生成能力会被下一代模型碾压，验证能力随模型变强而增值。判别工具是一个过滤器：假设 worker 无限聪明且诚实，这段代码还需要吗？需要的进 kernel/contract（升值），不需要的进 scaffolding（标注退役条件）。这是我做任何 Agent 项目的第一个资产分类动作。

**判断二：区分"客观事实"和"制度性事实"，是整个 Agent 治理的地基。**
机器可以去查"表里有没有 `create_day` 字段"（客观事实），但永远没有资格宣告"这个需求的生效范围是 6 月 1 日起"（制度性事实——那是业务方签字才能创造的事实）。模型能力越强，越危险：一个更强的模型不会停止越权裁决，只会把越权写得更流利、更自信。所以哪些环节必须人工签字，取决于该环节产出的是哪种事实，而不是模型够不够聪明。

**判断三："门禁过了"不等于"交付对了"。**
这个项目交付前的门禁（`hooks finalize`）有二十多道检查，但它只是"必要、远远不充分"的校验层。它检查文件存在、SQL 命中静态红线、release SQL 数量大于零——可它拦不住"结构不规范、范围不完整"的 release 被误判为可交付。这条教训的代价是一次真实的 release 漏项事故，见 [[04-真实复盘]] 里的 PM-018。

## 一个最贵的教训

> 完整版见 [[03-可迁移法则]] 法则 7：只看 RAW 工件，不看执行者叙述。

最初我让 Agent 写完一段分析就报告"已验证"。后来发现它在叙述里写"看起来像验证过"，但实际根本没跑查询。这不是它不诚实——是叙述本来就是它的输出，工件才是证据。从此以后，我的 review packet 固定开头永远是一句：**"请以 RAW gate 为准，不要根据 agent 叙述判断。"**

这条延伸出一个我自己很珍惜的观察：**我组织这个项目的方式，本身就是这个产品的同构物。** builder / executor / monitor / 外部 reviewer 的角色分离、拿证据包来评审、把裁定写回 contract——我在用治理 Agent 的方法治理"开发 Agent 的过程"。这个元技能比任何单条代码都值钱。

## 这个项目能证明什么

如果要把这份案例放到简历上，我会这样提炼它的可信度：

| 维度 | 证据 |
|---|---|
| **不是玩具** | 一个真实的、跨引擎（StarRocks / Hive / Presto / MySQL / 实时）的数据交付流水线，从需求采集到 release package 全链路有产物 |
| **有治理纪律** | S0–S4 五阶段门禁 + 交付前 finalize 汇总门禁；21 篇 postmortem（PM-001~021）把每次事故沉淀成结构化根因 |
| **可恢复、可审计** | 每个需求绑定 run id、timeline、checkpoint、approval、side-effect records；中断后能从 checkpoint resume |
| **知道边界在哪** | raw data / credential / 敏感 rowset 永不进入云端模型 context；Private Execution Gateway 在 cloud payload 上 fail-closed |
| **持续演进** | 从 v0.1 到 v1.0-rc，十几个 minor 版本，每个版本都有明确的治理主题，见 [[05-演进史]] |

`[真实产物 · 结构脱敏]` 一个需求工作区的典型产物骨架：

```text
output/demands/<demand_id>/
├── review/                  # 需求采集与评审（工单快照、effective requirements、质量报告、known fact resolution）
├── alignment.md             # 业务方签字的 alignment（制度性事实的唯一合法来源）
├── reference/               # S2/S3 工程产物（对象准入矩阵、scope convergence、evidence plan、probe evidence）
├── analysis.md              # 方案设计（口径、架构路径、实现拆解）
├── release_scope.yaml       # release obligation 契约（由签字 alignment 派生，不可手写）
├── release_manifest.yaml    # 由 CLI 机械派生，禁止直接编辑
├── release/                 # 分层 release 包
│   ├── 01_ddl/
│   ├── 02_etl/
│   ├── 04_validation/
│   └── 05_ops/
├── runs/<run_id>/           # runtime 真相（run.yaml、timeline.jsonl、checkpoint.json、policy_decisions.jsonl）
└── hooks/status.json        # 各阶段 gate 状态（PASS / WARN / BLOCKED）
```

这套结构不是设计出来的，是被 21 篇 postmortem 一篇一篇逼出来的。
